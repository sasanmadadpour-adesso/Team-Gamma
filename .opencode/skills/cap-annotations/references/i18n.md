# Multilingual labels and i18n — reference

## Ground rule: no hard-coded text

Every visible string belongs in the central i18n bundle. That includes labels in `@title`,
`@Common.Label`, `@UI.LineItem`, `@UI.HeaderInfo`, `@UI.FieldGroup`, `@Common.ValueList`,
and error messages in `@assert.*.message`.

Avoid:

```cds
{ Value: orderNo, Label: 'Order Number' }
@title: 'Customer'
@assert.format.message: 'Only uppercase letters allowed'
```

Prefer:

```cds
{ Value: orderNo, Label: '{i18n>OrderNo}' }
@title: '{i18n>Customer}'
@assert.format.message: '{i18n>msg_code_validation_pattern}'
```

## Where labels are defined

Labels follow **push-down**: the primary definition sits at the lowest layer where it
is still correct for every consumer. Deviations are overridden as close as possible
to the exception.

```
db/schema.cds                  ← inline @title for fields owned by the schema
db/labels.cds                  ← separate @Common.Label file (recommended for bigger projects)
srv/annotations/{svc}/labels.cds  ← service-wide overrides (rare; only when service deviates)
app/{app}/annotations/labels.cds  ← app-specific overrides (rare; only when one UI deviates)
app/{app}/annotations.cds      ← inline Label: (only when a single @UI snippet deviates)
```

> `srv/annotations/{svc}/labels.cds` and `app/{app}/annotations/labels.cds` are only loaded when
> they are imported — by `srv/annotations/{svc}/register.cds` (`using from './labels';`) and
> `app/{app}/annotations.cds` (`using from './annotations/labels';`) respectively. See *Wiring*
> in the parent `SKILL.md`.

**Why push-down?** A `@title` (or `@Common.Label`) defined once on the entity element
flows automatically into every service projection, every Fiori app, and every OData
$metadata stream. Defining the same label per app means maintaining the same string in
many places and risking drift; missing the file means half the UI ends up with technical
field names. One definition at the lowest valid layer is the cheapest, safest place.

### `@title` inline in `db/schema.cds`

`@title` is the CAP shorthand for `@Common.Label` — semantically identical, compiled into
OData metadata. Suitable for small to medium projects where the schema is the canonical
place to read field naming.

```cds
// db/schema.cds
entity Orders : cuid, managed {
  @title: '{i18n>OrderNo}'
  orderNo  : String(20);

  @title: '{i18n>Customer}'
  customer : Association to Customers;

  @title: '{i18n>Status}'
  status   : String(20);
}
```

Applies to all services that project this entity — no extra wiring.

### `db/labels.cds` (recommended for bigger projects)

For real projects with many entities, replicated S/4 views, generated types, or external
schemas you cannot edit inline, keep a dedicated `db/labels.cds`. The schema stays focused
on structure; the labels file becomes the single, scannable source for field naming and
makes incomplete labelling immediately visible.

```cds
// db/labels.cds
using { eam } from './schema';
using { eam.ownexternal as external } from './ownexternal';

// Centralised default @Common.Label annotations for every domain field.
// Apps and service projections may override per context (LineItem header,
// header-info title, value-help dialog) by setting their own @Common.Label —
// CAP picks the more specific annotation.

// ── eam.ChangeRequests ─────────────────────────────────────────────────────
annotate eam.ChangeRequests with {
    requestID         @Common.Label: '{i18n>RequestID}';
    status            @Common.Label: '{i18n>Status}';
    technicalObjectId @Common.Label: '{i18n>TechnicalObjectID}';
    // ...
};

// ── external (replicated S/4) ──────────────────────────────────────────────
annotate external.MaintenancePlan with {
    MaintenancePlan     @Common.Label: '{i18n>MaintenancePlan}';
    MaintenancePlanDesc @Common.Label: '{i18n>MaintenancePlanDescription}';
    // ...
};
```

> Labels for service-only artefacts (virtual fields, action parameters) have no
> DB counterpart and therefore live in the layer where the artefact is defined
> (typically `srv/` or `app/`).

### `srv/annotations/{svc}/labels.cds`

Only when a service must rename a field for **every** UI consuming it — i.e. all
apps of that service agree the field has a different name in that service context.
Rarely needed in practice.

### `app/{app}/annotations/labels.cds`

Only when one app needs a different label than the rest of the project, and the
deviation applies across every `@UI.*` annotation in that app.

```cds
// app/orders/annotations/labels.cds
using { OrdersService as service } from '../../../srv/orders-service';

// "customer" is shown as "Bill-to Party" throughout the orders app
annotate service.Orders with {
    customer @Common.Label: '{i18n>BillToParty}';
};
```

```cds
// app/orders/annotations.cds — imports the file, otherwise it is never loaded
using from './annotations/labels';
```

> If all labels match the DB layer → omit `labels.cds` entirely. The file exists
> only when there is a real, justifiable deviation.

### Inline `Label:` in `annotations.cds`

Only when a label deviates **in one specific UI element** (e.g. a short form in a
narrow table column):

```cds
// app/orders/annotations.cds
LineItem: [
  { Value: orderNo, Label: '{i18n>OrderNo_short}' },
]
```

### Decision tree

```
Is the label correct for every consumer of the field?
  YES → db/schema.cds (@title) or db/labels.cds (@Common.Label)
  NO
    Does every UI of the service share the same alternative?
      YES → srv/annotations/{svc}/labels.cds
      NO
        Does every @UI.* in the app share the same alternative?
          YES → app/{app}/annotations/labels.cds
          NO  → inline Label: on the specific @UI.* element
```

## Two bundles — strict separation

| Bundle | Content | CDS syntax | Loaded as |
|---|---|---|---|
| `i18n.properties` | Labels, field captions, UI texts in annotations | `{i18n>Key}` | `cds.i18n.labels` |
| `messages.properties` | **All error messages**: annotation constraint messages (`@assert…`, `@mandatory.message`) and runtime errors from `req.reject()` / `req.error()` | `'{i18n>msg_...}'` in annotations, `'PLAIN_KEY'` in code | `cds.i18n.messages` |

Labels and UI texts → `{i18n>Key}` → `i18n.properties`.
Annotation constraint messages → `'{i18n>msg_...}'` → `messages.properties`.
Raised via `req.reject(400, 'KEY')` → `UPPER_SNAKE_CASE` → `messages.properties`.

> **Why constraint messages are in `messages.properties`:** CAP resolves every validation
> message — the `then` texts of `@assert: (case …)` as well as `@assert.format.message`,
> `@assert.range.message` and `@mandatory.message` — from the **messages** bundle for the
> user's locale. A key that only exists in `i18n.properties` is not found, and the user sees
> the raw `{i18n>msg_…}` text (verified on CDS 10). The overrides for CAP's own messages
> (`ASSERT_FORMAT`, `ASSERT_RANGE`, `ASSERT_MANDATORY`, …) live in `messages.properties` too.

## Location: `_i18n/` at project root

```
_i18n/
├── i18n.properties           ← labels + UI texts, fallback
├── i18n_de.properties
├── i18n_en.properties
├── messages.properties       ← all error messages (annotation constraints + req.reject()), fallback
├── messages_de.properties
└── messages_en.properties
```

Use underscores in filenames — `i18n_de.properties`, not `i18n-de.properties`.

## Tag keys with origin comments

Because all layers write into one file, each key's origin must be obvious. Group
keys by source with comment blocks:

```properties
# _i18n/i18n.properties

# ── db/schema (global labels) ────────────────────────────────────
OrderNo=Order Number
Customer=Customer
Status=Status
Code=Code
CreatedAt=Created At

# ── app/orders ───────────────────────────────────────────────────
Order=Order
Orders=Orders
OrderNo_short=Order No.
GeneralData=General Information

# ── app/customers ────────────────────────────────────────────────
CustomerName=Customer Name
CustomerNo=Customer Number
Country=Country
```

```properties
# _i18n/messages.properties  (all error messages)

# ── db/schema (global constraint messages) ───────────────────────
msg_code_validation_pattern=Code must contain only uppercase letters, digits and underscores

# ── srv/orders-service (service-specific constraint messages) ─────
msg_customer_not_found=The specified customer does not exist
msg_begin_after_end=Begin date must be before end date

# ── srv/orders-service (req.reject) ──────────────────────────────
ORDER_EXCEEDS_STOCK=Order quantity {0} exceeds available stock by {1}
APPROVAL_NOT_ALLOWED=Approval is not allowed in status {0}
```

## Translation files: complete and consistent

Every key in `i18n.properties` / `messages.properties` (fallback) must exist in **every**
language file of the same bundle. Missing keys fall back silently to the default bundle —
without any warning.

```properties
# _i18n/i18n_de.properties

# ── db/schema ────────────────────────────────────────────────────
OrderNo=Bestellnummer
Customer=Kunde
Status=Status
Code=Code
CreatedAt=Erstellt am

# ── app/orders ───────────────────────────────────────────────────
Order=Bestellung
Orders=Bestellungen
OrderNo_short=Best.-Nr.
GeneralData=Allgemeine Informationen

# ── app/customers ────────────────────────────────────────────────
CustomerName=Kundenname
CustomerNo=Kundennummer
Country=Land
```

```properties
# _i18n/messages_de.properties

# ── db/schema ────────────────────────────────────────────────────
msg_code_validation_pattern=Code darf nur Großbuchstaben, Ziffern und Unterstriche enthalten

# ── srv/orders-service ───────────────────────────────────────────
msg_customer_not_found=Angegebener Kunde existiert nicht
msg_begin_after_end=Startdatum muss vor dem Enddatum liegen
ORDER_EXCEEDS_STOCK=Bestellmenge {0} übersteigt den verfügbaren Bestand um {1}
APPROVAL_NOT_ALLOWED=Genehmigung ist im Status {0} nicht erlaubt
```

## Key naming convention

Consistent names make search and maintenance trivial:

| Type | Pattern | Example |
|---|---|---|
| Entity (singular) | `{EntityName}` | `Order` |
| Entity (plural) | `{EntityName}s` | `Orders` |
| Field label | `{FieldName}` | `OrderNo`, `Customer` |
| Field label (variant) | `{FieldName}_{qualifier}` | `OrderNo_short` |
| Annotation constraint message (`messages.properties`) | `msg_{description}` | `msg_code_validation_pattern` |
| Runtime error (`req.reject`, `messages.properties`) | `UPPER_SNAKE_CASE` | `ORDER_EXCEEDS_STOCK` |
| UI section / facet | `{Name}` | `GeneralData`, `AddressData` |
